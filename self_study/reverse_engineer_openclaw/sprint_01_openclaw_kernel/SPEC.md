# SPEC: OpenClaw-Kernel

> Status: Sprint 01 working specification. This file is the highest technical constraint for Week 2 implementation.

## 1. Hard Constraints

Backend:

- Use FastAPI for HTTP boundaries.
- Use Pydantic for every external request and response contract.
- Do not reuse request schemas as response schemas unless the contract is intentionally identical.
- Use route -> service -> repository layering.
- Do not pass raw unvalidated dicts across boundaries.
- Route handlers must not directly access database sessions, ORM models, SQL, queue internals, or provider SDKs.
- Use SQLAlchemy async for persistence.
- Use Alembic for schema migration workflow.
- Use pytest for tests.

AI Gateway:

- Provide an SSE streaming response path.
- Provider calls must go through a provider adapter interface.
- Include a fake provider for deterministic tests.
- AWS Bedrock is the representative cloud-provider experiment when credentials are available.
- Timeout behavior must be explicit.
- Transient/rate-limit failures must retry only with bounded backoff.
- Permanent failures must fail fast.
- Token usage and estimated cost must be represented in the API, persistence, logs, or final metadata.

Async/Worker:

- Use `asyncio.Queue` only through a `QueueBackend` abstraction.
- Job state must be persisted or inspectable.
- The job table is the business state source of truth; the queue item is only an execution notification.

Frontend:

- Use Next.js 15, React, TypeScript, Tailwind CSS, and shadcn/ui where useful.
- The frontend is a minimum gateway console, not a polished product.
- It must submit messages, display streamed response text, and surface trace/cost/status metadata.

Observability:

- Use structlog or equivalent structured logging.
- Propagate `trace_id` across route, service, provider/worker, repository, and response metadata.
- Do not use `print()` in application code.

ADLC:

- Implementation must follow Ask -> Explore -> Plan -> Code -> Verify.
- Generated code is not accepted until it satisfies `TEST_PLAN.md`.
- Architecture decisions must align with `SYSTEM_DESIGN.md`.
- AI agents must follow `AGENT_RULES.md`.

## 4. SSE Rules

- The streaming endpoint must emit assistant text chunks.
- The stream must expose or return final metadata including trace_id and token/cost estimate.
- The stream must handle provider timeout or failure gracefully.
- The frontend must render incremental chunks, not wait only for the final response.
- Tests may use fake provider chunks instead of real provider tokens.

## 5. Provider Adapter Rules

Provider adapter implementations must not leak SDK-specific objects into route or service layers.

Minimum adapter behavior:

- accept normalized messages/prompt;
- accept model/provider settings;
- support streaming or clearly declare non-streaming limitation;
- classify errors as transient, rate_limited, timeout, permanent, or unknown;
- return normalized text chunks or final text;
- return token usage when available or allow fallback estimation;
- include trace_id in logs.

AWS Bedrock:

- is the preferred cloud-provider experiment because of learner familiarity with AWS;
- may be implemented as a real adapter if credentials are available;
- otherwise must have concrete setup notes and a fake/test adapter sharing the same interface.

## 6. Async Dispatch Rules

- Submitting a user message can create a job.
- The background path must not synchronously block the HTTP request until worker completion.
- Successful async message submission returns `202 Accepted`.
- Creating a user `Message` and its queued `Job` must happen in the same database transaction.
- The database commit for the user message and queued job must succeed before enqueueing the job.
- The worker consumes jobs from `QueueBackend`.
- The fake provider can simulate success, transient failure, rate limit, timeout, and permanent failure.
- Final job failure must be observable through job status and logs.

## 7. Persistence And Migration Rules

- Repositories may query and add ORM objects, but must not commit transactions.
- Service methods own business transaction boundaries using SQLAlchemy `AsyncSession.begin()` or an equivalent transaction manager.
- If job creation fails after user message creation, both the `Message` and `Job` must be rolled back.
- Queue enqueue must happen only after the database transaction commits successfully.
- If enqueue fails after commit, the persisted `Job` must remain in a recoverable state such as `enqueue_status = enqueue_failed`.
- The system must support a startup, scheduled, or explicit recovery scan for jobs with `status = queued` and `enqueue_status in (pending, enqueue_failed)`.
- Job recovery and multi-worker execution must be idempotency-aware; Sprint 01 may use simple status guards, but completed jobs must not be processed again.
- Alembic owns schema initialization and schema evolution for the main application schema.
- Application startup must not call `Base.metadata.create_all()` to manage the main application schema.
- Autogenerated Alembic migrations must be reviewed before being accepted.
- Migration files must be committed as part of the codebase.

## 8. TokenUsage Rules

- `TokenUsage` must be persisted as first-class gateway observability data.
- `TokenUsage` represents one provider invocation.
- `trigger_message_id` is required.
- `assistant_message_id` is nullable.
- `job_id` is nullable.
- The schema must allow multiple `TokenUsage` records for one triggering `Message` or `Job`.
- `confidence` is not part of `TokenUsage`.
- Sprint 01 does not implement a full billing system.

## 9. Failure Rules

- Invalid payloads fail at Pydantic boundary.
- Invalid client message role returns a validation error.
- Empty message content returns a validation error.
- Missing session returns a clear not-found error.
- Missing session must not persist a message or job.
- If database commit succeeds but enqueue fails, the failure must be observable through structured logs and persisted recoverable enqueue state.
- Transient provider failures may retry with bounded backoff.
- Rate-limit failures may retry if within configured retry budget.
- Timeout failures must be bounded.
- Permanent provider failures fail fast.
- Retry attempts must be logged.

## 10. Observability Rules

Every important log event should include:

- trace_id
- session_id when available
- message_id when available
- job_id when available
- provider when available
- model when available
- event name
- status or transition
- latency_ms when available
- token counts when available
- error type when applicable
